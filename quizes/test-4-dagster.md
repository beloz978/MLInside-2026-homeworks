Вопрос 1 🟩 понимание
Что верно про Dagster и Airflow 3? Несколько вариантов.

* ☑ ✅ В Dagster узел графа — ассет, то есть результат (таблица, файл, модель)
* ☐ В Airflow 3 планировать запуски по ассетам нельзя
* ☑ ✅ В Airflow 3 граф по-прежнему состоит из задач
* ☐ В Dagster lineage приходится описывать вручную
* ☑ ✅ В Airflow 3 ассет — событие, по которому запускается DAG

Разбор: Dagster описывает не «работу, которую надо выполнить», а результат. Зависимости задаются между ассетами, поэтому lineage строится сам, а проверки и метаданные привязаны к ассету. В Airflow 3 `@asset` упрощает запись и позволяет запускать DAG по событию, но единица графа по-прежнему задача.

Вопрос 2 🟩 понимание
Зачем ассету принимать ресурс параметром (например, `dwh`), а не создавать подключение внутри функции?

* А) Чтобы ассет выполнялся быстрее за счёт общего подключения
* Б) Чтобы менять подключение по окружениям, не правя код ассета ✅
* В) Чтобы Dagster шифровал данные, которые ассет читает и пишет
* Г) Чтобы каждый ассет запускался в отдельном процессе

Разбор: имя параметра совпадает с ключом в `Definitions(resources={...})`. Код ассета не знает, dev это или prod, — меняется только ресурс. В тесте в тот же параметр передают временную реализацию.

Вопрос 3 🟩 понимание
Кто отвечает за то, где лежит значение, которое вернул ассет, и откуда его возьмёт следующий ассет?

* А) IO manager ✅
* Б) Asset check
* В) Declarative automation
* Г) Партиции

Разбор: ассет делает только `return`, а сохранение и загрузку значения между ассетами берёт на себя IO manager (например, DuckDB, Parquet, BigQuery). Поменять хранилище можно, не трогая код ассетов.

Вопрос 4 🟨 применение
Расписание включено в интерфейсе, webserver работает, но запуски по времени не создаются. Какой компонент, скорее всего, не запущен?

* А) Не создан IO manager
* Б) Не собран `manifest.json`
* В) Не запущен dagster-daemon ✅
* Г) Не определён asset check

Разбор: webserver только показывает состояние. Тики расписаний и сенсоров, очередь запусков и automation выполняет daemon. Локально `dg dev` поднимает и webserver, и daemon, а в продакшене daemon нужно запускать отдельно.

Вопрос 5 🟨 применение
Сенсор следит за папкой и на каждый новый CSV создаёт запуск. Что гарантирует, что повторный тик не создаст второй запуск на тот же файл?

* А) Интервал опроса сенсора
* Б) `run_key` в `RunRequest` ✅
* В) Курсор сенсора
* Г) `partition_key` в `RunRequest`

Разбор: `run_key` (например, имя файла) — ключ идемпотентности: запуск с тем же `run_key` повторно не создаётся. Курсор нужен, чтобы не перебирать уже обработанное, а `partition_key` лишь говорит, какую партицию считать.

Вопрос 6 🟨 применение
Что происходит при подключении dbt-проекта через `dagster-dbt`? Несколько вариантов.

* ☑ ✅ Каждая dbt-модель становится ассетом
* ☑ ✅ dbt-тесты отображаются как asset checks
* ☐ SQL моделей выполняет сам Dagster вместо dbt
* ☑ ✅ Связи между ассетами строятся по `ref` и `source` из `manifest.json`

Разбор: SQL по-прежнему выполняет dbt (через `DbtCliResource`, обычно `dbt build`), а Dagster читает `manifest.json`, строит из него ассеты и lineage и показывает результаты тестов как проверки. Если ключи dbt-источников не совпадают с ключами raw-ассетов, граф получит разрыв: ключи задают через `meta.dagster.asset_key` или translator.

Вопрос 7 🟨 применение
После исправления логики ассета с daily-партициями нужно пересчитать последние 30 дней. Что использовать?

* А) Удалить и создать ассет заново
* Б) Backfill по диапазону партиций ✅
* В) Перезапустить daemon
* Г) Создать новый code location

Разбор: backfill запускает материализацию выбранных партиций, при этом каждая партиция считается идемпотентно, поэтому повторный пересчёт безопасен.

Вопрос 8 🟥 анализ
Из-за сбоя загрузки витрина иногда оказывается пустой, а обучение модели всё равно стартует и «успешно» завершается. Что лучше всего закроет проблему?

* А) Блокирующий asset check на витрине: `row_count > 0` ✅
* Б) RetryPolicy на ассете обучения с несколькими повторами
* В) Более частое расписание запуска витрины и обучения
* Г) Перенос ассета обучения в отдельный code location

Разбор: retry повторит запуск на тех же пустых данных, а частое расписание только умножит плохие запуски. Asset check с `blocking=True` (и серьёзностью ERROR) при провале не даёт выполниться зависимым ассетам в этом запуске, а с Declarative Automation то же даёт `all_deps_blocking_checks_passed`. Результат проверки (row_count) заодно остаётся в метаданных ассета.

Вопрос 9 🟨 применение
Как в pytest проверить два связанных ассета без БД и Docker?

* А) Запустить `dg dev` и прогнать оба ассета в интерфейсе
* Б) Поднять `dagster-daemon` и дождаться запуска по расписанию
* В) Вызвать `materialize_to_memory` с тестовыми ресурсами ✅
* Г) Запустить `dbt test` для моделей этих ассетов

Разбор: `materialize_to_memory` прогоняет цепочку настоящим механизмом Dagster, сам передаёт значения между ассетами и подставляет тестовые ресурсы. Отдельный ассет можно вызвать как обычную функцию. В CI дополнительно запускают `dg check defs`, чтобы убедиться, что определения загружаются.

Вопрос 10 🟥 анализ
Витрина `mart_order_features` лежит в code location `transform`, а `training_dataset` — в code location `ml`. Обучение должно стартовать после обновления витрины. Как это организовать?

* А) Импортировать код `transform` в `ml` и вызывать функцию витрины напрямую
* Б) Объединить всё в один code location, иначе lineage не построится
* В) Продублировать витрину в `ml` и обновлять её там отдельным ассетом
* Г) Сослаться на `AssetKey("mart_order_features")` и запускать по событию ✅

Разбор: ассеты разных code location связываются по ключу без импорта кода, и в интерфейсе это одно ребро графа. Но один запуск не материализует ассеты из разных locations, поэтому связывать их нужно событием: automation-условием на `training_dataset`, сенсором или расписанием. Раздельные locations — это независимые пакеты и образы, при общем графе.

Резерв вопросов (для второй версии теста или пересдачи)

Резерв 1 🟨 применение
Загрузка raw иногда опаздывает, и обучение по расписанию в 06:00 проходит на вчерашних данных. Чем лучше заменить расписание?

* А) Сдвинуть расписание обучения на час позже, на 07:00
* Б) Задать ассету обучения условие automation `eager` ✅
* В) Добавить RetryPolicy на ассет обучения и витрины
* Г) Запускать обучение вручную каждое утро после загрузки

Разбор: условие живёт на ассете и срабатывает по факту обновления upstream, а не по времени, поэтому в день опоздания загрузки обучение подождёт, а не пройдёт на вчерашних данных. Выполняет условия automation-сенсор внутри daemon, поэтому daemon нужен.

Резерв 2 🟨 применение
Что использовать, чтобы отправить сообщение в Telegram при падении запуска?

* А) `@dg.run_failure_sensor` ✅
* Б) `RetryPolicy`
* В) `AutomationCondition.eager()`
* Г) `DailyPartitionsDefinition`

Разбор: `run_failure_sensor` вызывается при падении запуска и получает контекст с информацией о сбое. `RetryPolicy` лишь повторяет шаг и никого не уведомляет, поэтому применяют оба: сначала повторы, потом оповещение.

Резерв 3 🟨 применение
Ассет иногда падает из-за временной недоступности внешнего API. Что добавить?

* А) Блокирующий asset check на результат ассета
* Б) `RetryPolicy` с задержкой на ассете ✅
* В) Daily-партиции для этого ассета
* Г) Второй экземпляр daemon для надёжности

Разбор: `RetryPolicy` повторяет упавший шаг (с `delay` и `backoff`), и временный сбой проходит без ручного перезапуска. Asset check проверяет результат, а не повторяет шаг; партиции и daemon с отказом внешнего API не связаны.

Резерв 4 🟩 знание
Как показать число загруженных строк рядом с ассетом в интерфейсе Dagster?

* А) Вернуть `MaterializeResult` с `metadata={"row_count": n}` ✅
* Б) Вывести число через `print` в теле ассета, чтобы оно попало в лог
* В) Записать число в README проекта вручную после запуска
* Г) Создать отдельный IO manager для хранения счётчика

Разбор: метаданные материализации хранятся вместе с ассетом, показываются в интерфейсе и по ним видна история между запусками. Вывод `print` остаётся в логах запуска и к ассету не привязан.

Резерв 5 🟥 анализ
После подключения dbt-проекта в графе есть raw-ассет `raw_orders` и dbt-модель `stg_orders`, но между ними нет связи. Что, скорее всего, не так?

* А) Не запущен dagster-daemon, который обновляет граф
* Б) У ассета `raw_orders` не настроен IO manager
* В) Ключ dbt-source не совпадает с ключом `raw_orders` ✅
* Г) У модели `stg_orders` слишком много партиций

Разбор: dagster-dbt строит связи по ключам ассетов; если ключ dbt-источника отличается от ключа raw-ассета, граф получает разрыв. Ключи выравнивают через `meta.dagster.asset_key` в описании source или через translator.
