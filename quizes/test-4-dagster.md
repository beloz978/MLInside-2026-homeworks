Вопрос 1 🟩 понимание · средний
Что верно про Dagster и Airflow 3? Несколько вариантов.

* ☑ ✅ В Dagster узел графа — ассет, то есть результат (таблица, файл, модель)
* ☐ В Airflow 3 планировать запуски по ассетам нельзя
* ☑ ✅ В Airflow 3 граф по-прежнему состоит из задач
* ☐ В Dagster lineage приходится описывать вручную
* ☑ ✅ В Airflow 3 ассет — событие, по которому запускается DAG

Подсказка: Подумайте, что в каждом инструменте является узлом графа, а что — событием между графами.

Разбор: Dagster описывает не «работу, которую надо выполнить», а результат. Зависимости задаются между ассетами, поэтому lineage строится сам, а проверки и метаданные привязаны к ассету. В Airflow 3 `@asset` упрощает запись и позволяет запускать DAG по событию (asset-aware scheduling), но единица графа по-прежнему задача.

Вопрос 2 🟩 понимание · простой
Зачем ассету принимать ресурс параметром (например, `dwh`), а не создавать подключение внутри функции?

* А) Чтобы ассет выполнялся быстрее за счёт общего подключения
* Б) Чтобы менять подключение по окружениям, не правя код ассета ✅
* В) Чтобы Dagster шифровал данные, которые ассет читает и пишет
* Г) Чтобы каждый ассет запускался в отдельном процессе

Разбор: имя параметра совпадает с ключом в `Definitions(resources={...})`. Код ассета не знает, dev это или prod, — меняется только ресурс. В тесте в тот же параметр передают временную реализацию. Ускорения, шифрования и отдельного процесса ресурс сам по себе не даёт.

Вопрос 3 🟩 понимание · простой
Кто отвечает за то, где лежит значение, которое вернул ассет, и откуда его возьмёт следующий ассет?

* А) IO manager ✅
* Б) Asset check
* В) Run storage
* Г) Executor

Разбор: ассет делает только `return`, а сохранение и загрузку значения между ассетами берёт на себя IO manager (например, `DuckDBPandasIOManager`, `FilesystemIOManager`). Поменять хранилище можно, не трогая код ассетов. Run storage хранит записи о запусках, а не данные; executor решает, как выполнять шаги (в одном процессе или в нескольких); asset check только проверяет результат.

Вопрос 4 🟨 применение · простой
Расписание включено в интерфейсе, webserver работает, но запуски по времени не создаются. Какой компонент, скорее всего, не запущен?

* А) IO manager
* Б) Code server
* В) dagster-daemon ✅
* Г) Run launcher

Разбор: webserver только показывает состояние. Тики расписаний и сенсоров, очередь запусков и automation выполняет daemon. Локально `dg dev` поднимает и webserver, и daemon, а в продакшене daemon нужно запускать отдельно. Без code server интерфейс показал бы ошибку загрузки code location; run launcher и IO manager — не отдельные процессы, а настройки, и до них дело доходит, только когда запуск уже создан.

Вопрос 5 🟨 применение · средний
Сенсор следит за папкой и на каждый новый CSV создаёт запуск. Что гарантирует, что повторный тик не создаст второй запуск на тот же файл?

* А) `minimum_interval_seconds` сенсора
* Б) `run_key` в `RunRequest` ✅
* В) Курсор сенсора
* Г) `partition_key` в `RunRequest`

Подсказка: Один механизм отвечает за «откуда продолжить», другой — за «не создавать уже созданное».

Разбор: `run_key` (например, имя файла) — ключ идемпотентности: запуск с тем же `run_key` повторно не создаётся. Курсор нужен, чтобы не перебирать уже обработанное, но сам по себе дубль не запрещает; `minimum_interval_seconds` задаёт только частоту тиков, а `partition_key` говорит, какую партицию считать.

Вопрос 6 🟨 применение · средний
Что происходит при подключении dbt-проекта через `dagster-dbt`? Несколько вариантов.

* ☑ ✅ Каждая dbt-модель становится ассетом
* ☑ ✅ dbt-тесты отображаются как asset checks
* ☐ Исполнение SQL моделей переходит от dbt к Dagster
* ☑ ✅ Связи между ассетами строятся по `ref` и `source` из `manifest.json`

Подсказка: Кто на самом деле выполняет SQL и из какого артефакта dbt Dagster берёт структуру проекта?

Разбор: SQL по-прежнему выполняет dbt (через `DbtCliResource`, обычно `dbt build`), а Dagster читает `manifest.json`, строит из него ассеты и lineage и показывает результаты тестов как проверки. Если ключи dbt-источников не совпадают с ключами raw-ассетов, граф получит разрыв: ключи задают через `meta.dagster.asset_key` или `DagsterDbtTranslator`.

Вопрос 7 🟨 применение · средний
После исправления логики ассета с daily-партициями нужно пересчитать последние 30 дней. Что использовать?

* А) Re-execute последнего запуска из интерфейса
* Б) Backfill по диапазону партиций ✅
* В) Wipe материализаций ассета
* Г) Reload code location

Подсказка: Нужно запустить материализацию сразу для многих партиций, а не повторить один запуск.

Разбор: backfill запускает материализацию выбранных партиций, при этом каждая партиция считается идемпотентно, поэтому повторный пересчёт безопасен. Re-execute повторит только последний запуск, то есть одну партицию; wipe лишь стирает историю материализаций и ничего не пересчитывает; reload подхватывает новый код, но запусков не создаёт.

Вопрос 8 🟥 анализ · сложный
Из-за сбоя загрузки витрина иногда оказывается пустой, а обучение модели всё равно стартует и «успешно» завершается. Что лучше всего закроет проблему?

* А) RetryPolicy на ассете обучения с несколькими повторами
* Б) Asset check `row_count > 0` на витрине с severity WARN
* В) Freshness check на витрине через `build_last_update_freshness_checks`
* Г) Блокирующий asset check на витрине: `row_count > 0` ✅

Подсказка: Нужна мера, которая не просто сообщает о проблеме, а не даёт выполниться зависимым ассетам.

Разбор: retry повторит запуск на тех же пустых данных. Обычная проверка с severity WARN пометит проблему, но обучение не остановит. Freshness check следит за тем, когда ассет обновлялся, а пустая витрина как раз обновилась вовремя. Asset check с `blocking=True` при провале не даёт выполниться зависимым ассетам в этом запуске, а с Declarative Automation то же даёт `all_deps_blocking_checks_passed`. Результат проверки (row_count) заодно остаётся в метаданных ассета.

Вопрос 9 🟨 применение · средний
Как в pytest проверить два связанных ассета без БД и Docker?

* А) Запустить `dg dev` и прогнать оба ассета в интерфейсе
* Б) Вызвать `dagster asset materialize --select ...` через subprocess
* В) Вызвать `materialize_to_memory` с тестовыми ресурсами ✅
* Г) Запустить `dbt test` в pytest-тесте для моделей этих ассетов

Подсказка: Ищите способ прогнать ассеты механизмом Dagster, но с подменёнными ресурсами и без внешних сервисов.

Разбор: `materialize_to_memory` прогоняет цепочку настоящим механизмом Dagster, сам передаёт значения между ассетами и подставляет тестовые ресурсы. CLI-материализация и `dg dev` используют настоящие ресурсы и IO manager, то есть ту самую БД; `dbt test` проверяет данные моделей, а не ассеты Dagster. Отдельный ассет можно вызвать как обычную функцию. В CI дополнительно запускают `dg check defs`, чтобы убедиться, что определения загружаются.

Вопрос 10 🟥 анализ · сложный
Витрина `mart_order_features` лежит в code location `transform`, а `training_dataset` — в code location `ml`. Обучение должно стартовать после обновления витрины. Как это организовать?

* А) Импортировать код `transform` в `ml` и вызывать функцию витрины напрямую
* Б) Объединить всё в один code location, иначе lineage не построится
* В) Продублировать витрину в `ml` и создать для неё там отдельный ассет
* Г) Указать `deps=[AssetKey("mart_order_features")]` и запускать по событию ✅

Подсказка: Ассеты разных code location видят друг друга по ключу, но в один запуск не попадают.

Разбор: ассеты разных code location связываются по ключу без импорта кода, и в интерфейсе это одно ребро графа. Но один запуск не материализует ассеты из разных locations, поэтому связывать их нужно событием: automation-условием на `training_dataset`, сенсором или расписанием. Раздельные locations — это независимые пакеты и образы, при общем графе.

Резерв 1 🟨 применение · средний
Загрузка raw иногда опаздывает, и обучение по расписанию в 06:00 проходит на вчерашних данных. Чем лучше заменить расписание?

* А) Сдвинуть расписание обучения на час позже, на 07:00
* Б) Расписанием `ScheduleDefinition` с cron каждые 5 минут
* В) Добавить RetryPolicy на ассет обучения и витрины
* Г) Задать ассету обучения условие automation `eager` ✅

Подсказка: Обучение должно зависеть от факта обновления данных, а не от времени.

Разбор: условие живёт на ассете и срабатывает по факту обновления upstream, а не по времени, поэтому в день опоздания загрузки обучение подождёт, а не пройдёт на вчерашних данных. Частое расписание всё равно привязано ко времени и будет переобучать модель без новых данных. Выполняет условия automation-сенсор внутри daemon, поэтому daemon нужен.

Резерв 2 🟨 применение · простой
Что использовать, чтобы отправить сообщение в Telegram при падении запуска?

* А) `@dg.run_failure_sensor` ✅
* Б) `@dg.asset_sensor`
* В) `AutomationCondition.eager()`
* Г) `AssetCheckSeverity.ERROR`

Разбор: `run_failure_sensor` вызывается при падении запуска и получает контекст с информацией о сбое; внутри него отправляют сообщение (для Slack есть готовый `make_slack_on_run_failure_sensor`). `asset_sensor` реагирует на материализацию ассета, а не на сбой; `eager` и severity к оповещениям не относятся. Повторы (`RetryPolicy`) и оповещение обычно ставят вместе: сначала повторы, потом сообщение.

Резерв 3 🟨 применение · простой
Ассет иногда падает из-за временной недоступности внешнего API. Что добавить?

* А) Блокирующий asset check на недоступность внешнего API
* Б) `RetryPolicy` с задержкой на ассете ✅
* В) Freshness check на ассет с допуском в один час
* Г) Второй экземпляр daemon для надёжности

Разбор: `RetryPolicy` повторяет упавший шаг (с `delay` и `backoff`), и временный сбой проходит без ручного перезапуска. Asset check и freshness check проверяют результат или его свежесть, а не повторяют шаг; второй daemon с отказом внешнего API не связан.

Резерв 4 🟩 знание · простой
Как показать число загруженных строк рядом с ассетом в интерфейсе Dagster?

* А) Задать `tags={"row_count": "..."}` в декораторе `@asset`
* Б) Вывести число через `context.log.info` в теле ассета
* В) Создать отдельный IO manager для хранения счётчика
* Г) Вернуть `MaterializeResult` с `metadata={"row_count": n}` ✅

Разбор: метаданные материализации хранятся вместе с ассетом, показываются в интерфейсе и по ним видна история между запусками (то же даёт `context.add_output_metadata`). Теги задаются при определении ассета и не меняются от запуска к запуску; лог остаётся в логах запуска и к ассету не привязан.

Резерв 5 🟥 анализ · сложный
После подключения dbt-проекта в графе есть raw-ассет `raw_orders` и dbt-модель `stg_orders`, но между ними нет связи. Что, скорее всего, не так?

* А) Ключ dbt-source не совпадает с ключом `raw_orders` ✅
* Б) У ассета `raw_orders` не настроен IO manager
* В) Не запущен dagster-daemon, который обновляет граф
* Г) У ассета `raw_orders` другой `group_name`

Подсказка: dagster-dbt связывает ассеты не по именам таблиц, а по ключам ассетов.

Разбор: dagster-dbt строит связи по ключам ассетов; если ключ dbt-источника отличается от ключа raw-ассета, граф получает разрыв. Ключи выравнивают через `meta.dagster.asset_key` в описании source или через `DagsterDbtTranslator`. Daemon граф не строит, IO manager отвечает за данные, а группа влияет только на отображение.

Резерв 6 🟩 знание · простой
Ассет нужно считать по дням, начиная с 2024-01-01. Что указать в `@asset(partitions_def=...)`?

* А) `StaticPartitionsDefinition([...])` со списком дат
* Б) `DailyPartitionsDefinition(start_date="2024-01-01")` ✅
* В) `TimeWindowPartitionMapping(start_offset=-1)`
* Г) `ScheduleDefinition(cron_schedule="0 0 * * *")`

Разбор: `DailyPartitionsDefinition` сам заводит партицию на каждый день от `start_date`. Статический список придётся дополнять вручную; `TimeWindowPartitionMapping` описывает, как партиции одного ассета зависят от партиций другого; расписание запускает, но партиций не задаёт.

Резерв 7 🟨 применение · средний
Ресурсу DWH нужен пароль. Как передать его, чтобы он не хранился в коде и не показывался в интерфейсе Dagster?

* А) Прочитать `os.getenv("DWH_PASSWORD")` при создании ресурса
* Б) Передать пароль через `run_config` при запуске
* В) Указать `password=dg.EnvVar("DWH_PASSWORD")` в ресурсе ✅
* Г) Положить пароль в `tags` ресурса в `Definitions`

Подсказка: Значение должно читаться в момент запуска, а в интерфейсе показываться только имя переменной.

Разбор: `EnvVar` читает значение в момент запуска, а в интерфейсе показывает только имя переменной. `os.getenv` читает значение при загрузке code location, и оно становится видно в интерфейсе; `run_config` и теги сохраняются вместе с запуском в открытом виде.

Резерв 8 🟨 применение · средний
Ассеты возвращают pandas DataFrame. Нужно, чтобы результаты сохранялись таблицами в DuckDB, а код ассетов не менялся. Что подключить под ключом `io_manager`?

* А) `DuckDBResource(database="olist.duckdb")`
* Б) `FilesystemIOManager(base_dir="data")`
* В) `mem_io_manager` из стандартной поставки
* Г) `DuckDBPandasIOManager(database="olist.duckdb")` ✅

Подсказка: Нужен IO manager, который сам пишет DataFrame в таблицу, а не просто даёт подключение.

Разбор: `DuckDBPandasIOManager` сам записывает возвращённый DataFrame в таблицу и читает его для следующего ассета. `DuckDBResource` даёт только подключение, и SQL пришлось бы писать в ассете; `FilesystemIOManager` сохраняет pickle-файлы, а `mem_io_manager` держит значения в памяти одного запуска.

Резерв 9 🟥 анализ · сложный
Витрину нужно пересчитывать сразу после обновления raw, но только если блокирующие проверки raw прошли. Какое условие задать витрине?

* А) `AutomationCondition.on_cron("0 6 * * *")`
* Б) `AutomationCondition.eager() & AutomationCondition.all_deps_blocking_checks_passed()` ✅
* В) `AutomationCondition.missing() & AutomationCondition.any_deps_updated()`
* Г) `AutomationCondition.eager() | AutomationCondition.all_deps_blocking_checks_passed()`

Подсказка: Обратите внимание на оператор между условиями: должны выполняться оба сразу.

Разбор: `eager()` срабатывает на обновление зависимостей, а `&` с `all_deps_blocking_checks_passed()` добавляет требование, что блокирующие проверки upstream прошли. С `|` хватило бы одного из условий, и витрина пересчиталась бы и на плохих данных. `on_cron` привязан ко времени, а `missing()` верно только для ни разу не материализованного ассета.

Резерв 10 🟨 применение · простой
Нужно материализовать `mart_order_features` вместе со всеми ассетами, от которых она зависит. Какой выбор ассетов взять?

* А) `AssetSelection.assets("mart_order_features").downstream()`
* Б) `AssetSelection.groups("mart_order_features")`
* В) `AssetSelection.assets("mart_order_features").upstream()` ✅
* Г) `AssetSelection.assets("mart_order_features")`

Разбор: `.upstream()` добавляет к ассету всё, от чего он зависит (в строке выбора то же даёт `+mart_order_features`). `.downstream()` берёт зависимые ассеты, `groups` ищет группу с таким именем, а выбор без модификатора материализует только саму витрину.
