Вопрос 1 🟩 знание
Что является основной единицей графа в Dagster?

* А) Задача (task)
* Б) Ассет (asset) ✅
* В) Оператор
* Г) Файл с DAG

Разбор: Dagster описывает не «работу, которую надо выполнить», а результат — таблицу, файл, модель. Зависимости задаются между ассетами, поэтому lineage строится сам. В Airflow 3 ассет — это событие между DAG, а единица графа по-прежнему задача.

Вопрос 2 🟩 понимание
Зачем ассету принимать ресурс параметром (например, `dwh`), а не создавать подключение внутри функции?

* А) Чтобы ассет выполнялся быстрее
* Б) Чтобы подменять подключение по окружениям (test / dev / prod) без правки кода ассета ✅
* В) Чтобы Dagster шифровал данные
* Г) Чтобы ассет запускался в отдельном процессе

Разбор: имя параметра совпадает с ключом в `Definitions(resources={...})`. Код ассета не знает, dev это или prod, — меняется только ресурс. В тесте в тот же параметр передают временную реализацию.

Вопрос 3 🟩 понимание
Кто отвечает за то, где лежит значение, которое вернул ассет, и откуда его возьмёт следующий ассет?

* А) IO manager ✅
* Б) Asset check
* В) Declarative automation
* Г) Партиции

Разбор: ассет делает только `return`, а сохранение и загрузку значения между ассетами берёт на себя IO manager (например, DuckDB, Parquet, BigQuery). Поменять хранилище можно, не трогая код ассетов.

Вопрос 4 🟨 применение
Расписание включено в интерфейсе, webserver работает, но запуски по времени не создаются. Какой компонент, скорее всего, не запущен?

* А) Не создан IO manager
* Б) Не собран `manifest.json`
* В) Не запущен dagster-daemon ✅
* Г) Не определён asset check

Разбор: webserver только показывает состояние. Тики расписаний и сенсоров, очередь запусков и automation выполняет daemon. Локально `dg dev` поднимает и webserver, и daemon, а в продакшене daemon нужно запускать отдельно.

Вопрос 5 🟨 применение
Сенсор следит за папкой и на каждый новый CSV создаёт запуск. Что гарантирует, что повторный тик не создаст второй запуск на тот же файл?

* А) Интервал опроса сенсора
* Б) `run_key` в `RunRequest` ✅
* В) Курсор сенсора
* Г) `partition_key` в `RunRequest`

Разбор: `run_key` (например, имя файла) — ключ идемпотентности: запуск с тем же `run_key` повторно не создаётся. Курсор нужен, чтобы не перебирать уже обработанное, а `partition_key` лишь говорит, какую партицию считать.

Вопрос 6 🟨 применение
Что происходит при подключении dbt-проекта через `dagster-dbt`? Несколько вариантов.

* ☑ ✅ Каждая dbt-модель становится ассетом
* ☑ ✅ dbt-тесты отображаются как asset checks
* ☐ SQL моделей выполняет сам Dagster вместо dbt
* ☑ ✅ Связи между ассетами строятся по `ref` и `source` из `manifest.json`

Разбор: SQL по-прежнему выполняет dbt (через `DbtCliResource`, обычно `dbt build`), а Dagster читает `manifest.json`, строит из него ассеты и lineage и показывает результаты тестов как проверки. Если ключи dbt-источников не совпадают с ключами raw-ассетов, граф получит разрыв: ключи задают через `meta.dagster.asset_key` или translator.

Вопрос 7 🟨 применение
Раньше витрину и обучение модели запускали расписанием в 06:00, но загрузка raw иногда опаздывает. Чем здесь лучше условие Declarative Automation (например, `eager`) на самом ассете?

* А) Выполняется быстрее, чем запуск по расписанию
* Б) Заменяет asset checks
* В) Не требует работающего daemon
* Г) Привязано к обновлению зависимостей, а не ко времени: в день опоздания загрузки обучение подождёт, а не пройдёт на вчерашних данных ✅

Разбор: условие живёт на ассете и срабатывает по факту обновления upstream. Условия можно комбинировать: `eager() & all_deps_blocking_checks_passed()` — пересчёт сразу после обновления, но только если блокирующие проверки зависимостей пройдены; `on_cron` — пересчёт по времени, когда зависимости обновились. Выполняет условия automation-сенсор внутри daemon, поэтому daemon нужен.

Вопрос 8 🟥 анализ
Из-за сбоя загрузки витрина иногда оказывается пустой, а обучение модели всё равно стартует и «успешно» завершается. Что лучше всего закроет проблему?

* А) Блокирующий asset check на витрине (например, `row_count > 0`) ✅
* Б) RetryPolicy на ассете обучения
* В) Более частое расписание
* Г) Перенос обучения в другой code location

Разбор: retry повторит запуск на тех же пустых данных, а частое расписание только умножит плохие запуски. Asset check с `blocking=True` (и серьёзностью ERROR) при провале не даёт выполниться зависимым ассетам в этом запуске, а с Declarative Automation то же даёт `all_deps_blocking_checks_passed`. Результат проверки (row_count) заодно остаётся в метаданных ассета.

Вопрос 9 🟨 применение
Как в pytest проверить цепочку из двух ассетов без БД, Docker и MLflow-сервера?

* А) Запустить `dg dev` и открыть интерфейс
* Б) Поднять `dagster-daemon`
* В) Вызвать `materialize_to_memory([...], resources={...})` с тестовыми ресурсами ✅
* Г) Запустить `dbt test`

Разбор: `materialize_to_memory` прогоняет цепочку настоящим механизмом Dagster, сам передаёт значения между ассетами и подставляет ресурсы, а результат берём через `output_for_node`. Отдельный ассет можно вызвать как обычную функцию (с `build_asset_context()`, если нужен context). В CI дополнительно запускают `dg check defs`, чтобы убедиться, что определения загружаются.

Вопрос 10 🟥 анализ
Витрина `mart_order_features` лежит в code location `transform`, а `training_dataset` — в code location `ml`. Обучение должно стартовать после обновления витрины. Как это организовать?

* А) Импортировать код `transform` в `ml` и вызывать функцию витрины напрямую
* Б) Объединить всё в один code location, иначе lineage не построится
* В) Продублировать витрину в `ml`
* Г) Сослаться на ключ `AssetKey("mart_order_features")` и запускать обучение условием automation или сенсором ✅

Разбор: ассеты разных code location связываются по ключу без импорта кода, и в интерфейсе это одно ребро графа. Но один запуск не материализует ассеты из разных locations, поэтому связывать их нужно событием: automation-условием на `training_dataset`, сенсором или расписанием. Раздельные locations — это независимые пакеты и образы, при общем графе.

Резерв вопросов (для второй версии теста или пересдачи)

Резерв 1 🟨 применение
После исправления логики ассета с daily-партициями нужно пересчитать последние 30 дней. Что использовать?

* А) Удалить и создать ассет заново
* Б) Backfill по диапазону партиций ✅
* В) Перезапустить daemon
* Г) Создать новый code location

Разбор: backfill запускает материализацию выбранных партиций, при этом каждая партиция считается идемпотентно, поэтому повторный пересчёт безопасен.

Резерв 2 🟨 применение
Что использовать, чтобы отправить сообщение в Telegram при падении запуска?

* А) `@dg.run_failure_sensor` ✅
* Б) `RetryPolicy`
* В) `AutomationCondition.eager()`
* Г) `DailyPartitionsDefinition`

Разбор: `run_failure_sensor` вызывается при падении запуска и получает контекст с информацией о сбое. `RetryPolicy` лишь повторяет шаг и никого не уведомляет, поэтому применяют оба: сначала повторы, потом оповещение.

Резерв 3 🟥 анализ
Чем ассет в Airflow 3 принципиально отличается от ассета в Dagster?

* А) Ничем: это одно и то же
* Б) В Airflow планировать по ассетам нельзя
* В) В Airflow ассет — событие между DAG, а единица графа остаётся задачей; в Dagster ассет — сам узел графа ✅
* Г) В Dagster нет lineage

Разбор: в Airflow 3 `@asset` упрощает запись и позволяет запускать DAG по событию, но граф по-прежнему состоит из задач. В Dagster граф строится из ассетов, поэтому lineage, проверки и метаданные привязаны к самому результату.
